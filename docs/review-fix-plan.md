## 1. Запуск участника комнаты при медленной загрузке

**Реализовано.** Участник запускает поток на паузе и ждёт актуальную позицию ведущего с запасом 1,5 с в одном непрерывном буфере. Готовность фрагмента не перезапускает HLS. Коррекция внутри буфера сохраняет поток; для длительного отставания разрешён один повтор после 30 с ожидания. Явная перемотка или смена источника ведущим создают новую попытку. Ведущий видит ожидающих участников и кнопку общей паузы, участник — повтор подключения. Пауза ведущего сохраняет приоритет.

**Причина.** Ведущий продолжает смотреть, пока участник загружает первый фрагмент. На `canplay` вычисляется новая позиция ведущего. Если она ещё не попала в буфер участника, `PP.seek()` уничтожает текущий HLS и запускает следующий. При длительной загрузке ситуация повторяется после каждого запуска.

**Нужное поведение.** Участник накапливает пригодный буфер, затем синхронизируется и начинает просмотр. Полученные фрагменты сохраняются. Очень медленное соединение приводит к понятному состоянию ожидания, а не к циклу запуска FFmpeg. Состояние ведущего не меняется автоматически из-за одного ожидающего участника.

**Выполненный план:**

1. Разделить состояния участника: загрузка источника, ожидание подходящего буфера, воспроизведение, коррекция позиции. Одна входящая команда комнаты должна иметь одно поколение запуска.
2. Добавить в интерфейс плеера проверку, доступна ли абсолютная позиция в текущем непрерывном буфере, и перемотку без перезапуска. События готовности должны проверять буфер, а не принудительно запускать новый поток.
3. При первом запуске ждать появления актуальной позиции ведущего в буфере. Если данных недостаточно, продолжать загрузку и показывать «Синхронизируем просмотр».
4. Для отставания за пределами буфера предусмотреть один контролируемый повтор синхронизации после готовности потока, с отдельным бюджетом попыток и интервалом. Повторные `canplay`, `playing` и ответы опроса не должны расходовать новые попытки для одной команды.
5. Небольшую разницу исправлять перемоткой внутри буфера; изменение источника, серии или явная перемотка ведущего создают новое поколение. Пауза ведущего имеет приоритет над ожидающим автозапуском.
6. После исчерпания времени/попыток показывать причину ожидания и действие повторного подключения. Ведущему показывать ожидающего участника и возможность поставить всех на паузу для накопления данных.

**Проверки:** первый фрагмент длится 6 с и поступает за 7–15 с; задержка дорожек; вступление во время паузы; быстрая смена серии и перемотка ведущего; сеть медленнее битрейта; восстановление после временного обрыва.

**Готово, когда:** медленный старт не порождает бесконечные HLS-запуски, участник начинает просмотр при достаточном буфере, а после стабилизации соединения расхождение укладывается в установленный допуск 0,35 с. При недостаточной пропускной способности отображается ожидание без непрерывных перезапусков.

**Основные файлы:** `web/watch-room.js`, `web/player.js`, тесты комнаты и плеера.

## 3. Старый таймер удаления продлённого кеша

**Реализовано.** Обработчик под блокировкой проверяет, что его таймер и торрент всё ещё актуальны, срок хранения истёк и нет читателей или подготовки файлов. Продление кеша, повторное открытие и замена торрента делают старый обработчик недействительным. После закрытия менеджера поздний ответ не создаёт новые таймеры. Учёт заблокированных файлов сохранён.

**Причина.** `Timer.Stop()` не останавливает уже выполняющийся обработчик. Пока обработчик ждёт mutex, `Keep()` может продлить срок хранения. Старый обработчик затем вызывает удаление без проверки нового срока.

**Выполненный план:**

1. Хранить поколение расписания удаления для каждого infohash. Продление, отмена и новое открытие должны делать старое расписание недействительным.
2. В обработчике, под тем же mutex менеджера, проверить поколение, текущий срок `keepUntil`, читателей и запросы подготовки файлов.
3. При продлённом сроке запланировать удаление на новый момент; при активных читателях оставить удаление на закрытие последнего читателя. Удалять только после всех проверок.
4. Не позволять старому обработчику отменять новый таймер или удалять новую сессию с тем же hash.
5. Учесть повторное удаление заблокированных файлов: состояние ожидающего удаления сохраняется по исправлению пункта 4.

**Проверки:** остановленный таймер уже ждёт mutex; продление `Keep()` перед выполнением старого обработчика; открытие читателя; завершение срока без читателей; несколько последовательных продлений; повторное открытие того же hash.

**Готово, когда:** старый обработчик не удаляет продлённый кеш, актуальный срок продолжает соблюдаться, таймеры не накапливаются, действующие читатели защищены.

**Основные файлы:** `internal/torrents/manager.go` и тесты жизненного цикла кеша.

## 6. Временная недоступность базы и авторизация

**Реализовано.** Истёкшая сессия получает `401`, временный сбой — `503` с `auth_unavailable`, отсутствие настроенной базы — `503` с `auth_disabled`. Интерфейс сохраняет профиль и уже загруженную историю при сбое и повторяет проверку через 2, 4, 8, 16, затем до 30 с с небольшим разбросом. Защищённые действия при ошибке базы запрещены. Поколение авторизации защищает от поздних ответов проверки профиля, загрузки истории, сохранения позиции и удаления истории после выхода или повторного входа, включая вход в тот же аккаунт. Неудачное удаление не очищает локальную историю.

**Причина.** `currentUser()` возвращает одинаковый результат для отсутствующей сессии и ошибки базы. API выдаёт `401`, интерфейс очищает пользователя. Сейчас `503` также означает отключённую авторизацию, поэтому одного изменения HTTP-статуса недостаточно.

**Выполненный план:**

1. Разделить три результата проверки: действующая сессия; отсутствующая/истёкшая сессия; ошибка сервиса. Передавать ошибку из `currentUser()` вызывающему обработчику.
2. Оставить `401` только для недействительной сессии. Для временного сбоя возвращать `503` со стабильным кодом `auth_unavailable`; отсутствие настроенной базы обозначать отдельным кодом `auth_disabled`.
3. На фронтенде очищать профиль только после подтверждённого `401` или явного выхода. При временном сбое сохранить отображаемый профиль и уже загруженную историю, показать краткое состояние недоступности.
4. Добавить повторную проверку с увеличением интервала, например 2, 4, 8, 16, 30 с, с небольшим случайным разбросом. Одна вкладка не должна запускать несколько параллельных циклов.
5. Отменять старые запросы при выходе или смене пользователя, чтобы поздний ответ не восстановил предыдущий профиль.
6. Проверить все защищённые обработчики: кеш профиля используется только для отображения. Сервер по-прежнему проверяет права и при недоступности базы не разрешает защищённые действия.

**Проверки:** перезапуск базы с действующей cookie; восстановление базы; реальное истечение сессии; отключённая авторизация; ошибка сети; выход во время ожидающего запроса; защищённые операции при сбое базы.

**Готово, когда:** временный сбой не выглядит как выход из аккаунта, профиль и история восстанавливаются без повторного входа, реальные истёкшие сессии обрабатываются корректно, права доступа не ослаблены.

**Основные файлы:** `internal/authapi/auth.go`, зависимые обработчики проверки пользователя, `web/shared.js` и тесты авторизации.

## 8. IPTV после HTTP-перенаправления

**Реализовано.** Корневые и вложенные плейлисты разрешают относительные ссылки от конечного адреса HTTP-ответа. Это относится к сегментам, вложенным спискам, ключам и инициализационным сегментам. Передача User-Agent, Referer и Range сохранена. Факт перенаправления и сетевые ошибки записываются без адреса и приватных параметров. Причина ошибки остаётся доступна для внутренней проверки таймаутов и отмены.

**Причина.** Плейлист читается по конечному адресу перенаправления, но относительные ссылки разрешаются от первоначального URL. Это касается и корневых, и вложенных плейлистов.

**Выполненный план:**

1. Использовать конечный адрес `resp.Request.URL` как базу переписывания корневого плейлиста.
2. Применить тот же подход к вложенному плейлисту в обработчике сегментов.
3. Проверить все переписываемые ссылки: сегменты, вложенные списки, ключи шифрования и инициализационные сегменты. Абсолютные ссылки должны сохранять смысл.
4. Сохранить текущую передачу User-Agent/Referer и обработку Range. Исправление адреса не должно менять эти параметры.
5. В диагностике отличать ошибку получения плейлиста от ошибки получения сегмента и указывать факт перенаправления без вывода приватных токенов.

**Проверки:** `302` на другую папку и другой домен; цепочка перенаправлений; вложенный перенаправленный плейлист; относительные и абсолютные URI; `EXT-X-KEY`, `EXT-X-MAP`; поток без перенаправления.

**Готово, когда:** плейлист после перенаправления загружает существующие сегменты без ошибочного `502`, а потоки без перенаправления продолжают работать.

**Основные файлы:** `internal/iptvapi/stream.go` и HTTP-тесты IPTV.

## 9. Возврат в комнату через «Назад» браузера

**Реализовано.** При `pageshow` комната получает свежую позицию и восстанавливает присутствие с одним циклом опроса. Ответы, начатые до `pagehide`, игнорируются; роль ведущего сохраняется, закрытая комната снимает ограничения участника. При сохранении страницы браузером (`persisted`) плеер не уничтожает HLS и буфер; обычный таймаут неактивной серверной сессии остаётся в силе.

**Причина.** `pagehide` останавливает опрос комнаты. При восстановлении страницы из кеша браузера скрипт не запускается заново, а обработчика `pageshow` нет.

**Выполненный план:**

1. Добавить обработчик восстановления страницы (`pageshow`, включая `event.persisted`).
2. Сбросить устаревший образец состояния ведущего и немедленно получить актуальное состояние комнаты до продолжения синхронизации.
3. Восстановить регистрацию присутствия и один цикл опроса. Повторные события не должны создавать дополнительные таймеры.
4. Сохранить роль ведущего/участника. Если комната закрыта, корректно снять режим участника и показать сообщение.
5. Защитить новое состояние поколением запроса, чтобы ответ, начатый до `pagehide`, не перезаписал восстановленную комнату.

**Проверки:** события `pagehide`/`pageshow` с `persisted`, несколько возвратов, смена позиции/серии ведущим во время отсутствия, закрытие комнаты, ответ старого запроса. События восстановления проверены в Chromium и модульных тестах. Фактическое попадание страницы с медиаплеером в back/forward cache не проверено: это зависит от браузера и условий навигации.

**Готово, когда:** после возврата возобновляются опрос и присутствие, применяется актуальная позиция, работает ровно один цикл, закрытая комната не сохраняет ограничения участника.

**Основные файлы:** `web/watch-room.js`, связанные обработчики присутствия и браузерные тесты.

## 12. Безопасная пагинация каталога

**Реализовано.** Отсутствующие параметры используют прежние значения по умолчанию; пустые, повторные, нечисловые и выходящие за диапазон параметры получают `400` с `invalid_pagination`. Размер страницы ограничен 100 записями; существующие клиенты используют 10 или 30. Проверка количества страниц до умножения защищает `SearchPage` от переполнения даже при максимальном `int`. Корректная страница за пределами каталога возвращает пустой список и общее количество.

**Причина.** Большой положительный `page` проходит разбор числа, но `(page - 1) * perPage` переполняет `int`. Отрицательная граница среза вызывает панику в публичном обработчике.

**Выполненный план:**

1. Зафиксировать контракт: отсутствующие параметры используют значения по умолчанию; явно некорректные или не представимые целые числа получают `400` с понятным кодом ошибки.
2. Ограничить `per_page` до 100 после проверки существующих клиентов. Проверять параметры на границе HTTP API.
3. В `SearchPage` сначала сравнивать запрошенную страницу с числом доступных страниц через деление, затем вычислять смещение. Защита должна работать и при прямом вызове метода из Go.
4. Проверять конец диапазона через оставшееся число элементов, без потенциально переполняющего сложения.
5. Для корректной страницы за пределами каталога возвращать `200`, пустой список и исходное общее количество записей.

**Проверки:** пустой каталог; первая и последняя страницы; страница за пределами каталога; ноль, отрицательное, нечисловое значение; максимальный `int`; число за пределами `int`; слишком большой `per_page`; прямой вызов `SearchPage`.

**Готово, когда:** никакие параметры пагинации не вызывают панику; обычный каталог и поиск сохраняют совместимость; некорректный запрос получает контролируемый ответ.

**Основные файлы:** `internal/catalogapi/catalog.go`, обработчик `/api/catalog` и тесты каталога.

## Итоговая проверка

- Общий прогон: 435 проверок Go и 148 проверок JavaScript прошли.
- В Chromium прошли сценарии комнаты, временного сбоя авторизации и восстановления, страниц фильмов и сериалов в обеих темах, выбора источника и озвучки. Плеер отдельно проверен на настоящих HLS-фрагментах и WebVTT-субтитрах, созданных FFmpeg.
- 11 интеграционных проверок Go пропущены: для них нужны отдельная тестовая PostgreSQL или явно включённые проверки живых внешних источников. Рабочая база не использовалась.
- Восстановление комнаты проверено через события жизненного цикла страницы; фактическая доступность browser back/forward cache не подтверждена. При `pagehide` с `persisted:true` запрос остановки серверной HLS-сессии не отправляется.
